**Applies to:** PDF exports and print-ready documents generated by the React/Tauri frontend.  
**Package:** `pdfmake@0.3.13` (MIT), bundled locally by Vite.

## Product rule

Use the shared implementation in `frontend/src/lib/pdfmake.ts` for new frontend PDF generation. Do not add CDN scripts, direct `window.print()` document rendering, or a second browser-side PDF library.

The shared helpers are:

- `downloadInstitutionalPdf(options)` — create and download a PDF.
- `printInstitutionalPdf(options)` — open the generated PDF in the browser's print flow.
- `openInstitutionalPdf(options)` — open a generated PDF for preview.

Document definitions should be built from live, authorized API data already available to the screen. Do not fabricate totals, balances, grades, names, payment statuses, or other institutional records.

## Branding and offline behavior

- PDFMake and its font virtual file system are imported from npm and bundled locally; no CDN or runtime internet access is required.
- The shared engine uses the locally embedded Roboto font supplied by PDFMake. This is separate from the UI's self-hosted fonts.
- Pass the active institution's name, motto, contact details, and primary colour from the institution settings context when that data has loaded and is active.
- Never hardcode an institution name or use a stale local branding value in a newly generated document.
- The shared helper validates the colour and falls back to a neutral institutional green when no valid active colour is supplied.
- Keep the login page, login CSS, and login assets outside PDF-related changes.

## Document quality

- Use A4 portrait by default; use landscape for wide tables and timetables.
- Use repeated table headers for multi-page tabular documents.
- Include a descriptive filename, document title, page numbering, and appropriate metadata.
- Use `en-UG` date and number formatting where the document represents Ugandan institutional records; use UGX for school finance unless an explicitly approved multi-currency feature is introduced.
- Ensure the generated document remains readable when printed in grayscale.
- Keep sensitive fields to the minimum required and preserve the same authorization checks as the screen/API.

## Architecture boundary

Uploaded student documents and other user-supplied attachments are stored and downloaded in their original file format. PDFMake is for generating SMIS documents and reports; it must not silently convert or modify uploaded source files.

PDFMake is a JavaScript library. The React/Tauri frontend can use it directly and it is bundled for offline use. Existing .NET API PDF endpoints currently use QuestPDF in the backend. Those endpoints remain server-generated and retain their backend authorization and data integrity controls; do not replace them with client-side PDFMake or move sensitive report data into the browser merely to force one library across different runtimes. A future backend migration would require an explicit .NET/JavaScript document-service architecture decision.

## Remaining migration work

- Audit every newly added document/export surface against this standard before release.
- Review backend-only PDF endpoints still generated by QuestPDF. The React/Tauri UI uses PDFMake, but the .NET API retains QuestPDF for compatibility and server-side consumers; replacing that runtime requires a separate approved architecture change.
- Keep CSV/XLSX exports in their appropriate formats; PDFMake is not a replacement for spreadsheet export.
